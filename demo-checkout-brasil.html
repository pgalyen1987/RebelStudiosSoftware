Type a bad CPF and watch it get caught

The complaint that made this plugin exist is that the alternatives add the fields and then do not check them, so the store finds out the document is wrong when the invoice is rejected. These are the real checks, running here in the page.

CPF

Official mod-11 check digits. The eleven repeated-digit strings are rejected too — they satisfy the arithmetic but are not issuable, and they are what gets typed when someone wants the field to go away.

CNPJ, and the company name that comes with it

Validated the same way, then looked up in the public company registry through BrasilAPI. A valid CNPJ fills in the Razão Social.

CEP, and the address that comes with it

Eight digits and the street, neighbourhood, city and state appear, from ViaCEP. Try 01310-100.

If a lookup service is down the customer simply types the address. The purchase is never blocked by a third-party API — that is deliberate, and you can test it by going offline.

What this page is, exactly. It runs the plugin's own validation — the mod-11 routines from class-cb-validator.php, unchanged — and calls the same two lookup providers. Two honest differences: in the plugin those lookups run from your server and are cached, not from the browser, so no customer data passes through anyone else; and validation runs again server-side, because a browser check alone can be skipped. The rest of the plugin is the part a page cannot show — the documents carried onto the order, the admin, the emails and the REST API for your NF-e integration, HPOS storage, the per-field Off / Optional / Required settings, and LGPD export and erasure. The interface ships in Portuguese (pt-BR) by design.
